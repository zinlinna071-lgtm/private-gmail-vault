# Ciphertext-Only Vault API Contract

**Status:** Design contract for the client-side encryption migration  
**Branch:** `feature/vault-authentication`  
**Production impact:** None. This document does not apply database migrations, change live data, merge, or deploy.

## 1. Security boundary

The API authenticates the Supabase session and enforces ownership. It does not unlock or decrypt the Vault.

The API must never receive or return:
- Account names, usernames, passwords, or backup codes in plaintext
- The Master Password
- The Argon2id output / Key Encryption Key (KEK)
- The unwrapped Data Encryption Key (DEK)

The browser owns all encryption and decryption. The database stores opaque authenticated ciphertext and public protocol metadata only. Authentication success does not imply Vault unlock.

## 2. Vault and record identifiers

The current product is single-user and has one Vault per authenticated account. Use the authenticated Supabase `user.id` UUID as the immutable `vaultId` for AAD binding; do not accept a client-supplied owner or vault identifier.

Each account entry has a random UUID `recordId` generated by the browser before encryption. The same ID is used as the database row primary key and as the record ID in AES-GCM additional authenticated data.

The existing `vault_items.user_id` column remains the ownership boundary. Every read, update, and delete must filter by the authenticated `user.id`, regardless of the record ID supplied by the client.

## 3. Record envelope v1

The browser sends this JSON object to create or update a record:

```json
{
  "version": 1,
  "algorithm": "AES-256-GCM",
  "iv": "<canonical-base64-12-byte-nonce>",
  "ciphertext": "<canonical-base64-ciphertext>",
  "authTag": "<canonical-base64-16-byte-tag>"
}
```

Validation requirements:
- Reject unknown object fields and unknown protocol versions.
- Require the exact algorithm identifier `AES-256-GCM`.
- Require a 12-byte IV and a 16-byte authentication tag.
- Require canonical Base64 encoding.
- Reject empty ciphertext and enforce the 20,000-byte plaintext-equivalent ciphertext limit before database writes.
- Never accept client-supplied user IDs, vault IDs, timestamps, or ownership fields.
- Never attempt to decrypt or semantically inspect the ciphertext on the server.

The record AAD is constructed in the browser from the protocol domain, version, authenticated `user.id` (the Vault ID), record UUID, and record type. Changing any context value must make decryption fail.

## 4. API behavior after the UI migration

### GET /api/vault/items
- Authenticate the session.
- Select only rows owned by the authenticated user.
- Return each row's ID, opaque ciphertext envelope, and timestamps.
- Do not call server-side decryption or read a server encryption key.

### POST /api/vault/items
- Require same-origin, JSON content type, and a bounded streamed request body.
- Authenticate the session.
- Validate the record UUID and envelope shape.
- Insert the opaque ciphertext fields and authenticated user ID.
- Return only the stored envelope and non-secret metadata.

### PUT /api/vault/items/:id
- Require same-origin, JSON content type, and a bounded streamed request body.
- Authenticate the session and validate the UUID.
- Update only the row matching both record ID and authenticated user ID.
- Store the opaque envelope without decrypting it.

### DELETE /api/vault/items/:id
- Require same-origin and authenticate the session.
- Delete only the row matching both record ID and authenticated user ID.

All responses containing Vault records must use `Cache-Control: no-store`. Errors must not echo request bodies, ciphertext, credentials, or key material.

## 5. Existing data and compatibility

The current `vault_items` table has `id`, `user_id`, `ciphertext`, `iv`, and `auth_tag` columns. Existing rows were encrypted by the server-side legacy scheme. They are **not** client-side v1 envelopes, even if they use AES-GCM.

Do not silently treat legacy rows as client-side records. Before enabling the new API against a database containing old rows:
1. Add an explicit encryption-scheme/version marker with a migration that classifies existing rows as legacy.
2. Keep legacy reads isolated and clearly marked as temporary; do not expose them as zero-knowledge.
3. Design and test a user-mediated browser migration that obtains plaintext only in the authenticated browser, decrypts the legacy row using the legacy mechanism, encrypts it with the newly unlocked client DEK, and writes the new envelope.
4. Verify migration completion and backup/restore behavior before removing legacy support.

Do not apply this schema migration to any live Supabase project from this branch. First inspect the actual target database and obtain explicit approval for any live migration.

## 6. Rollout gates

- Keep the existing UI and API contract in sync; do not switch the API to ciphertext-only while the UI still sends plaintext.
- Test record creation, listing, update, delete, tampering, wrong AAD, wrong key, malformed envelopes, oversized streamed requests, cross-user access, and session expiry.
- Inspect browser network requests to confirm only ciphertext and public metadata leave the browser.
- Inspect server logs and error responses for accidental plaintext/key leakage.
- Verify legacy data handling and recovery before calling the product zero-knowledge.
- Remove the server-side account-data encryption path and its key only after all compatibility and recovery gates pass.

This contract describes the intended API. Until the routes and UI are migrated and independently verified, the running application remains server-readable and is not zero-knowledge.
