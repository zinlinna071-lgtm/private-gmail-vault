# Authentication Vault — TOTP and Google Backup-Code Design

**Project:** Private Gmail Vault  
**Branch:** `feature/vault-authentication`  
**Status:** Design proposal only; no schema or runtime changes in this document.  
**Date:** 2026-11-06

## 1. Purpose

Allow the owner to retrieve a time-based one-time password (TOTP) or an unused Google backup code from the Vault on a replacement device after losing the primary phone and SIM.

The owner must enroll the Vault as an authenticator while they still have access to the Google account. The Vault cannot recover an existing TOTP seed from Google or create a factor that Google has not enrolled.

## 2. Required user journey

### Before device loss

1. The owner opens Google Account Security and starts Google's official 2-Step Verification setup.
2. The owner chooses an authenticator-app method and deliberately enrolls the Vault by entering the setup key or scanning the displayed QR code using a trusted Vault enrollment screen.
3. Google asks for a first TOTP code to confirm enrollment; the owner enters the code generated by the Vault.
4. The Vault stores the TOTP seed only after successful confirmation.
5. The owner optionally imports Google backup codes generated by Google and confirms that they have been saved.
6. The owner keeps an independent offline backup of Vault access and recovery material.

### During emergency

1. The owner opens the Vault on a new device.
2. The owner signs in with the independent Vault Login ID and Master Password, without relying solely on the lost phone or SIM.
3. The owner completes any additional Vault unlock step.
4. The owner opens Authentication Vault and selects the relevant Google account.
5. The Vault reveals a current TOTP code or an unused Google backup code after a fresh authentication check.
6. The owner manually enters the factor into Google's own sign-in challenge.
7. Google decides whether the factor and the overall sign-in attempt are accepted.

## 3. Critical security boundary

- Google remains the authority for sign-in verification and account recovery.
- The Vault does not approve Google Prompts, intercept challenges, automate Google sign-in, or bypass Google's risk checks.
- TOTP only works if the corresponding seed was enrolled with that Google account beforehand and Google offers the authenticator method for the current challenge.
- Google backup codes are generated by Google, are single-use, and must be marked consumed after use.
- The Vault cannot guarantee account recovery if Google requires an unavailable factor or rejects the recovery attempt.

## 4. Proposed cryptographic architecture

Do not reuse Gmail OAuth refresh-token encryption fields or the existing server-only pending-Recovery-Code encryption format for authenticator seeds.

### Client-side key hierarchy

1. At enrollment, generate a random per-Vault data-encryption key (DEK) using a cryptographically secure random generator.
2. Generate a unique random KDF salt for the Vault's secret store.
3. Derive a key-encryption key (KEK) from the user's Master Password using a reviewed, memory-hard password KDF (prefer Argon2id; use a documented fallback only if the supported runtime cannot provide it).
4. Wrap the DEK using authenticated encryption (AES-256-GCM or XChaCha20-Poly1305) with a versioned envelope and fixed context/AAD identifying the Vault user and purpose.
5. Encrypt each TOTP seed and backup-code collection with the DEK using a fresh nonce and per-record AAD.
6. Store only ciphertext, nonce, authentication tag, KDF parameters, salt, and version metadata in the database.
7. Keep the unwrapped DEK only in short-lived application memory after successful unlock. Clear it on sign-out, lock, timeout, or page teardown as far as the runtime allows.

### Threat-model requirements

- Do not send the derived KEK or unwrapped DEK to server APIs.
- Do not put plaintext secrets in localStorage, sessionStorage, URLs, logs, analytics, error reports, or browser caches.
- Keep decrypted values out of React server props and server-rendered HTML.
- Use strict Content Security Policy, avoid third-party scripts, and review all client dependencies for XSS exposure.
- Require a fresh unlock before revealing/copying a TOTP or backup code.
- Explain that a compromised browser/device or malicious extension can still capture a displayed code.
- The Vault Recovery Code must not silently decrypt the secret store. A separate, explicitly designed recovery-key mechanism would be required if password-loss recovery of encrypted factors is desired.

## 5. Data model proposal (not yet a migration)

A private table such as `vault_authenticator_items` may contain:
- `id`, `user_id`, optional `gmail_connection_id`
- `label`, `issuer`, `account_hint`, `factor_type`
- `secret_ciphertext`, `secret_nonce`, `secret_auth_tag`
- `wrapped_dek_ciphertext`, `wrapped_dek_nonce`, `wrapped_dek_auth_tag`
- `kdf_name`, `kdf_version`, `kdf_salt`, `kdf_parameters`
- `encryption_format_version`, timestamps, and disabled/deleted state

Google backup codes should be stored as individually encrypted records or as a separately encrypted set with a per-code consumed state. Never store plaintext codes or a plaintext hash that could be used to validate guessed values.

All tables must have RLS enabled, no browser-facing grants, service-role access only through authenticated server routes for metadata operations, and user-id scoping on every query. Secret encryption and decryption remain client-side.

## 6. TOTP requirements

- Implement RFC 6238 with HMAC-SHA1 as the interoperable default unless Google enrollment requirements are verified to support another algorithm.
- Support 6 digits and a 30-second time step as the initial profile.
- Validate seed encoding and lengths; never accept arbitrary otpauth URLs without strict parsing and validation.
- Use a trusted system clock and show a clear countdown.
- Do not persist generated TOTP values.
- Test time-window boundaries, clock skew handling, malformed seeds, and known RFC test vectors.

## 7. Backup-code lifecycle

- Import only codes explicitly generated by Google and entered by the owner.
- Normalize formatting for comparison/display but preserve no plaintext copy after encryption.
- Display one code at a time after fresh unlock.
- Require the owner to mark a code as used after Google accepts it; explain that the Vault cannot independently verify Google's acceptance.
- Never offer a consumed code again.
- Support replacing the entire set when the owner generates a new Google backup-code set.
- Keep a separate offline backup; do not make the Vault the only copy.

## 8. Enrollment and recovery UX

- Clearly label each item as TOTP Authenticator or Google Backup Code.
- Show enrollment state: Not enrolled, Pending confirmation, Active, or Disabled.
- Do not mark a TOTP item Active until Google confirms enrollment through the owner's manual verification step.
- Provide reveal/copy actions only after fresh unlock.
- Provide explicit lock and sign-out controls.
- Make it clear that Google may request another factor even when a valid TOTP or backup code is available.

## 9. Required tests before implementation is considered complete

- KDF parameter validation and version migration.
- DEK wrapping/unwrapping and wrong-password failure.
- Ciphertext tamper detection and AAD cross-user isolation.
- No plaintext secrets in API responses, logs, server-rendered HTML, or browser storage.
- TOTP RFC vectors and time-step boundaries.
- Backup-code single-use state and replacement flow.
- Authorization isolation between Vault users.
- Fresh-unlock enforcement for reveal/copy.
- XSS/CSP and dependency review.
- Replacement-device test with a dedicated Google test account.

## 10. Rollout boundary

This document does not authorize or perform:
- Supabase schema migrations or live database changes.
- Vercel environment-variable or secret changes.
- Google account or production Gmail changes.
- Token re-encryption or OAuth scope expansion.
- Merge to `main` or production deployment.

Implementation must begin only after the key hierarchy, browser threat model, recovery trade-offs, and schema are reviewed. The owner must approve the migration and any live secret changes separately.

**Design principle:** The Vault may safely preserve factors the owner enrolled and stored beforehand; Google alone decides whether those factors satisfy a sign-in challenge.
